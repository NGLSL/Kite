Status: ready-for-agent
Type: enhancement

## Problem Statement

Kite 已具备多路召回、统一最终排序、匹配证据、查询偏好、Pin 与启动组归并。对照 ZeroLaunch-rs、LaunchyQt、Flow Launcher、ZTools 的源码分析后，真正缺的不是再换一套 matcher，而是四类能力缺口：

1. **匹配位置与原文字段不对齐。** 部分拼音、词元、跳字证据仍写成占位起点或未知位置；同分细排因此不稳定，后续结果高亮也拿不到可信位置。Flow 的做法是拼音文本与原名称建立 TranslationMapping，命中位置映射回原文。
2. **拼音/明确别名等字段的容错验证不完整。** 删除索引可能已召回拼音候选，但末端验证未按原字段做同等的真实编辑距离检查；用户把全拼打错一两个字母时，召回靠拼音、验证却退回中文名称，结果丢失。ZeroLaunch 的做法是各搜索关键词（含拼音）都参与同一套容错评分。
3. **连续输入仍由 UI 同步阻塞。** 普通应用搜索在 `refresh_results` 中同步完成，并在此读取历史；旧查询没有协作取消，相同 Query 重复计算，新输入被拖慢。Flow 的程序搜索在后台执行并传取消令牌，且带查询缓存与索引失效。
4. **用户只能“常选谁”，不能“别再推谁”。** 偏好只表达正向选择；没有有限、可撤销的降权标记。LaunchyQt 提供 demoteItem。评分过程也缺少可解释明细，排错只能靠截图猜。

用户会感到：同样的输入有时顺序说不清；打错拼音容易找不到；连打字会卡；不想要的结果一直靠前；维护者解释不了“为什么第二”。

## Solution

在保留 Kite 现有统一最终排序、质量层、明确匹配保护、Pin 与启动组归并的前提下，补四项能力：

```text
字段位置映射（拼音/词元/跳字 → 原名称位置）
        ↓
字段级受限纠错验证（复用删除索引，按所属字段验证真实距离）
        ↓
统一搜索服务（常驻工作线程 · 最新优先 · 旧任务取消 · 代际核对 · 小缓存）
        ↓
个性化扩展（可撤销降权）＋ 评分诊断明细
        ↓
     最终 TopK
```

具体体验：

- **位置可信**：可映射的拼音/词元命中记录原名称起点与跨度；不可映射时明确标为未知，不当作最佳位置；同分时更早、更紧凑、更少跳空稳定靠前。
- **字段容错**：`jisunqi` 能召回「计算器」一类全拼字段；纠错仍受长度与距离上限约束，单字母/极短简拼不无限放宽。
- **连续输入流畅**：最新 Query 优先；旧任务协作取消；结果按查询与索引代际核对后才合并；匹配缓冲可复用；相同 Query 的基础匹配证据可小容量缓存，历史偏好仍用最新状态重算。
- **用户可纠正**：对结果执行“降低此结果优先级”后，该入口在后续排序中被降权；可恢复。不修改扫描结果与启动目标。
- **开发者可解释**：诊断路径输出「命中字段 → 验证方式 → 基础分 → 偏好分 → 归并到哪个入口」，用于解释排序而不是替代最终排序。

## User Stories

1. 作为 Kite 用户，我希望拼音命中也能定位到中文名称上的真实起始位置，以便同分时更自然的命中靠前。
2. 作为 Kite 用户，我希望拼音字段被映射失败时不要假装命中在名称最前面，以免未知位置抢赢真实前缀命中。
3. 作为 Kite 用户，我希望词元/关键词命中尽量带真实字段与起点，以便排序结果更可预期。
4. 作为 Kite 用户，我希望有序跳字/多词命中记录真实间隔，以便紧凑匹配优于散落匹配。
5. 作为 Kite 用户，我希望以后结果高亮能复用同一份位置证据，以免排序和显示两套位置。
6. 作为 Kite 用户，我希望把「计算器」的全拼 `jisuanqi` 误打成 `jisunqi` 时仍能找到，以便拼音字段也享受容错。
7. 作为 Kite 用户，我希望明确别名/关键词的拼音在受限纠错下也能召回，以便不必死记精确拼写。
8. 作为 Kite 用户，我希望纠错仍限制编辑距离与最短长度，以免短查询把大量无关应用召回。
9. 作为 Kite 用户，我希望纠错候选是否保留由对应字段的真实验证决定，而不是召回通道的删除深度，以免通道自删正确候选。
10. 作为 Kite 用户，我希望规则对所有应用一致，不写产品名专属分支，以便新装软件获得同样体验。
11. 作为 Kite 用户，我希望连续输入时界面响应最新 Query，不被前一次查询拖住。
12. 作为 Kite 用户，我希望旧查询在新输入到来后尽快取消，以免过时结果闪回或挤占计算。
13. 作为 Kite 用户，我希望返回的结果一定属于当前 Query 与当前索引代际，以免索引刷新后显示过期列表。
14. 作为 Kite 用户，我希望重复输入相同内容时尽量少做重复匹配计算，以便回删/重打更流畅。
15. 作为 Kite 用户，我希望缓存只加速基础匹配证据，历史偏好仍按最新状态计算，以便刚启动的应用立刻参与竞争。
16. 作为 Kite 用户，我希望索引变化、纠错规则变化或代际切换时缓存失效，以免用旧候选解释新索引。
17. 作为 Kite 用户，我希望缓存不要只缓存截断后的 Top N，以免历史偏好救不回被截掉的候选。
18. 作为 Kite 用户，我希望对当前结果执行“降低此结果优先级”，以便该入口不再总是抢在前面。
19. 作为 Kite 用户，我希望降权可以恢复，以免误操作后永久失去候选。
20. 作为 Kite 用户，我希望降权只影响排序，不删除索引项、不改启动目标，以便应用仍可被正确启动。
21. 作为 Kite 用户，我希望明确匹配保护与 Pin 语义不被降权静默破坏；若冲突，行为可预期且可测试。
22. 作为 Kite 用户，我希望空 Query 的固定与最近使用列表逻辑保持稳定习惯。
23. 作为 Kite 用户，我希望文件、网页、系统入口边界不被本轮应用排序改动破坏。
24. 作为维护者，我希望能在诊断中看到候选的命中字段、验证方式、基础分、偏好分与归并目标，以便解释“为什么没找到/为什么第二”。
25. 作为维护者，我希望诊断挂在统一搜索入口的调试产物上，而不是另开一套排序器。
26. 作为维护者，我希望后台搜索服务有独立可测缝：提交 Query、最新优先、取消、代际核对，而不依赖真实 UI。
27. 作为维护者，我希望 UI 只做薄适配（提交查询、接收结果、按代际丢弃），主逻辑可单测。
28. 作为维护者，我希望本轮不引入新的外部搜索引擎、向量检索或重型任务框架。
29. 作为维护者，我希望实现顺序为：位置映射 → 字段受限纠错 → 搜索服务 → 降权与诊断，以便每步可独立验收。
30. 作为维护者，我希望相对既有搜索 eval 基线无显著回退，且新增样本覆盖本轮关键行为。

## Implementation Decisions

- 保留现有统一最终排序入口与显式质量层；本轮增强 MatchEvidence 位置、字段级受限纠错、搜索服务与可撤销降权，不重开 matcher 选型。
- **位置映射**：索引/预计算在生成拼音、紧凑文本等派生字段时，同时保留与原名称的对应关系（或等价可反查映射）。验证阶段把派生字段命中映射回原名称字符位置；可映射则写真实 start/span，不可映射则记未知（不得写成 0/最优）。词元与有序多词证据继续用真实字段与间隔，禁止统一占位。
- **同分细排**继续使用既有证据比较键（更早起点 / 更少跳空 / 更低代价 / 更长覆盖），并与明确匹配保护、统一最终比较器共存；无个性化与有个性化路径共用同一证据规则。
- **字段级受限纠错**：删除索引候选必须能追溯原词元及所属字段（名称/显示名/Alias/关键词/拼音等）。验证时对对应字段计算真实编辑距离（或等价代价）；禁止用查询侧删除深度是否为 0 代替验证。纠错距离、最短查询长度、极短简拼策略保持受限；不新增第二套拼写引擎。
- **搜索服务**：为普通应用搜索提供常驻工作线程（或等价调度器）。接口语义：提交带查询与代际的请求；优先处理最新请求；旧请求协作取消；完成结果必须核对查询与索引代际后才能合并；失败/取消不得污染当前列表。
- **缓冲与缓存**：允许复用 matcher/工作缓冲；允许小容量缓存「相同规范化 Query 的候选集与基础匹配证据」。个性化（Usage/Recency/Query 配对/Pin/降权）始终用最新内存/存储状态重算。索引代际变化、匹配规则变化时缓存失效。禁止只缓存截断后 Top N 再当全集。
- **降权与恢复**：增加有限、可撤销的用户降权标记（按稳定应用身份持久化，遵守 rusqlite 历史存储约定）。降权在截断前进入个性化加分/排序链，效果是降低 FinalScore 或等价负偏好，不删除 AppItem、不改 target/args。与 Pin、明确匹配保护的优先关系须显式定义并写入测试：默认降权不能被历史正向偏好轻易抵消，也不得把受保护精确匹配静默打到无关弱匹配之后——若保护与降权冲突，采用“仍可召回但不再抢前排”的有限策略，而不是隐藏候选。
- **评分诊断**：在统一搜索入口提供调试产物（非默认 UI 噪音）：对进入排序的候选给出 命中字段 → 验证方式 → 基础分 → 偏好分（历史/Pin/降权）→ 归并后的展示/启动入口。诊断不得分叉排序逻辑，只读同一条链。
- **UI**：搜索输入改为向搜索服务提交；接收结果时核对代际。右键/结果菜单增加“降低此结果优先级”与“恢复优先级”。不在 UI 层重写排序。
- 不改变扫描、启动、图标、Everything、托盘与空 Query 列表语义；不引入新外部搜索栈。
- 多名称搜索、单结果展示继续走既有启动组归并，不为 ZTools 再立新项目。

## Testing Decisions

- 好测试只断言外部可见行为：给定固定应用索引、Query、可选个性化/降权状态与（服务缝）代际，观察最终 TopK 的身份与相对顺序、是否丢弃过时结果、降权是否生效可恢复；不断言内部函数调用次数或具体分值常量。
- **主测试缝（正确性）**：`search_with_personalization` / `RetrievalIndex::search_personalized` / `search_system_personalized`。位置映射的排序效果、字段纠错召回、降权排序全部走此缝。
- **服务测试缝（仅后台调度）**：搜索服务入口——提交请求、注入慢任务、断言最新优先、旧任务取消、代际不匹配结果被丢弃、相同 Query 缓存加速后基础证据一致且偏好仍最新。UI 不做主测。
- **辅助单测（仅当主缝无法隔离）**：
  - MatchEvidence 比较与未知位置语义；
  - 删除索引 expand 返回的查询侧删除深度语义（文档化）；
  - 存储层降权标记的写入/读取/恢复；
  - 诊断结构字段完整性（只读，不反推排序）。
- 必测行为样本：
  1. 拼音字段容错：索引含「计算器」及其全拼时，`jisunqi` 能召回该应用（允许非首位，不得消失）；对照正确全拼 `jisuanqi` 不回退。
  2. 位置映射：两个同分候选中，可映射为更早/更紧凑原名称位置者靠前；未知位置不得战胜真实前缀位置。
  3. 纠错不误杀：词典/字段含 `chrome` 时 `crome` 仍可召回；真实距离验证决定保留，不由删除深度 0 直接跳过。
  4. 服务代际：旧查询完成时若已有更新查询或更高代际，旧结果不得替换当前列表。
  5. 降权：降权后该入口相对同等质量未降权候选后移；恢复后回到原规则；启动目标未变。
  6. 保护不回退：Name Exact / 用户 Alias 仍受明确匹配保护；上一轮偏好与 Pin 样本不回退。
  7. 产品名中立：不得出现针对具体软件名称的打分分支。
- prior art：沿用 `search` 模块统一入口回归测试、`history` 分层/保护不变量、`tests/search_cases.json` 与 eval 基线；服务缝可参考现有文件查询 generation 模式的测试风格。本轮以新增构造样本为主，不依赖 Windows 实机截图验收算法正确性。
- 检查通过标准：`cargo test` 全绿；新增样本覆盖上述必测项；相对既有 required eval 无显著回退；真机连续输入体验由实现者在 Windows 上做一次冒烟（非算法验收门槛）。

## Out of Scope

- 引入 Skim、复制 LaunchyQt 比较器、换成 Fuse.js、搜索引擎切换菜单或可插拔引擎框架。
- Flow 的双拼/整套词组多音字词典维护；本轮不替换 ib-pinyin。
- 负反馈学习模型、几十个可调评分参数、云端同步。
- 把诊断做成完整可视化产品面板（有结构化输出即可）。
- Everything 文件搜索重写、扫描管线重构、启动器协议扩展。
- 与四款参考软件的实机速度对比或承诺倍数。
- 重新设计 MatchScore 常量表、重做短输入策略、取消前缀词元固定枚举上限的专项优化。
- 图标、托盘、安装器、UI 视觉、签名与发布流程。
- 为任何品牌或 exe 写特例。
- 许可层面的源码直接复制：本规格只借鉴规则并在 Kite 代码中自行实现。

## Further Notes

- 前序：`search-experience-next` → `search-quality-feedback` → `search-quality-gaps`（统一排序、质量层、证据贯穿、纠错语义、混输分档）。本规格是参考项目源码分析后的**能力补齐**，不推翻上述正确性修复；若与 `search-quality-gaps` 的证据占位修复重叠，以本规格的“位置映射 + 未知不当最优”为完成标准，避免两套位置语义。
- 建议实现顺序：
  1. **字段位置映射**（拼音/词元 → 原名称位置；同分细排受益）
  2. **拼音/明确别名等字段的受限纠错验证**（复用删除索引 + 字段追溯 + 真实距离）
  3. **常驻搜索工作线程、取消、缓冲复用、小容量基础证据缓存、代际核对**
  4. **可撤销降权 + 评分诊断**（存储 + Personalization + 调试产物 + 结果菜单）
- 多名称覆盖（ZTools）不在此规格重复立项；依赖既有启动组归并。
- 领域词汇沿用 `docs/CONTEXT.md`：AppItem、Query、MatchScore、Alias、Usage、Recency、Query History、FinalScore、明确匹配保护、Pin。本规格新增长期概念建议后续补入领域文档：**匹配位置证据（原名称 start/span/未知）**、**降权（可撤销负偏好）**、**搜索代际（Query + 索引版本）**、**评分诊断**。
- 存储遵循 ADR 0001（rusqlite + 手写 SQL + user_version 升级）；降权表变更需可升级。
- 与 ADR 0002（Everything 文件搜索）无冲突：本轮不改文件搜索协议，只保证应用搜索服务不破坏既有文件结果合并边界。
- 引用来源仅作分析依据：ZeroLaunch-rs 标准搜索模型与评分明细、LaunchyQt Catalog 匹配与 demoteItem、Flow Launcher StringMatcher / PinyinAlphabet / 程序搜索取消与缓存、ZTools 多名称字段与去重展示。最终以 Kite 自身实现与测试为准。
