Type: enhancement

## Problem Statement

上一轮 `search-quality-feedback` 已把「先截断再加分」「UI 抹掉质量层」「单字符/混输召回」主流程修到位，方向正确，应保留。但源码复核表明：匹配证据在验证阶段算对了，却没有真正贯穿到最终列表；纠错通道仍会把「输入直接命中删除变体」当成无距离而丢掉候选；混输高分分支过宽，容易把片段碰巧命中抬到与有序混拼音同权。

用户仍会感到：

1. **同样是同分命中，有时排得莫名其妙。** 证据已算出「起点更早、间隔更小」，最终同分却回退到稳定 ID / 名称长度，细排效果被抹掉。这不是历史偏好改变结果，而是证据在物化展示对象时丢了。
2. **明显拼写错误有时纠不回来。** 例如词典有 `chrome`、用户输入 `crome`，查询侧删除深度为 0 被当作「不是纠错」直接跳过，该纠错通道自删候选。
3. **混输一下出来很多弱关联高分。** 汉字段与拉丁段分别在名称/拼音/词元中碰巧出现即可拿到整词级高分，未检查先后顺序与位置复用。

根因不是缺新算法，而是少数关键位置仍在丢弃已经算对的信息。

## Solution

在保留现有统一最终排序、质量层与查询偏好的前提下，把三条信息流真正接到最终列表：

```text
候选 ID ＋ 基础 MatchScore ＋ 质量层 ＋ 匹配证据
                    ↓
            应用查询偏好 / Pin
                    ↓
          统一比较器完成最终排序
                    ↓
              截取 Top N
                    ↓
           才物化 SearchResult
```

具体体验：

- **同分可解释**：同基础分时，连续、词边界、起点更早、间隔更小的匹配稳定靠前，不被稳定 ID 或名称长度覆盖；有无个性化时同分规则一致。
- **纠错不误杀**：输入直接命中词典词的删除变体时，候选保留；是否符合纠错距离由真实验证决定，不由查询侧删除次数冒充。
- **混输分强弱**：按名称顺序完成的混合拼音/英文对齐继续可得高分；仅「各片段分别碰巧出现」的跨字段证据作宽召回，不直接获得整词级高分。
- **证据位置可信**：词元、有序多词、拼音等占位位置（起点 0 / gaps 0）逐步换成真实位置；未知位置不得当作最佳位置。

## User Stories

1. 作为 Kite 用户，我希望两个同分候选中命中位置更靠前者排在前面，以便顺序可预期且不被内部 ID 抖动影响。
2. 作为 Kite 用户，我希望有无历史偏好时，同分细排规则保持一致，以便个性化不会意外改变证据胜负。
3. 作为 Kite 用户，我希望空历史时同分也先比匹配证据，再比名称长度和名称，以便「更紧凑的命中」始终优先。
4. 作为 Kite 用户，我希望输入 `crome` 时 Google Chrome 仍能进入候选，以便少打一个字符也能纠回来。
5. 作为 Kite 用户，我希望纠错候选是否保留由真实编辑距离验证决定，以免通道自己把对的词丢掉。
6. 作为 Kite 用户，我希望纠错通道语义可区分「查询侧删除深度」和「与原词的真实距离」，以便实现与测试不会再次误过滤。
7. 作为 Kite 用户，我希望混输 Query 中汉字段与拉丁段按名称顺序对齐时仍可高分，以便「微信xin」类输入不回退。
8. 作为 Kite 用户，我希望仅片段分别碰巧出现、未按顺序对齐的混输结果不得与有序混拼音同权，以便弱关联不抢前排。
9. 作为 Kite 用户，我希望混输验证不要重复使用同一名称位置同时满足多个片段，以便高分对应真实覆盖。
10. 作为 Kite 用户，我希望音节级匹配器认可的对齐继续作为强证据，宽召回分支不得绕过它直接给整词分。
11. 作为 Kite 用户，我希望词元命中证据尽量记录真实字段与起点，而不是统一写成名称起点 0，以便同分比较公平。
12. 作为 Kite 用户，我希望有序多词命中记录真实间隔，而不是统一 gaps=0，以便紧凑匹配优于散落匹配。
13. 作为 Kite 用户，我希望拼音相关证据的起点在可映射时映射回原名称位置，不可映射时视为未知而非最佳，以便不把未知当成赢点。
14. 作为 Kite 用户，我希望上一轮已修好的「偏好在截断前生效」和「质量层不被 UI 抹掉」继续有效，以便本轮不回退。
15. 作为 Kite 用户，我希望完整名称精确匹配与用户 Alias 仍受明确匹配保护，以便纠错与混输改动不越权。
16. 作为 Kite 用户，我希望空 Query 固定项与最近使用列表不受本轮影响，以便默认习惯不变。
17. 作为 Kite 用户，我希望文件、网页、系统入口结果边界不被本轮应用排序改动破坏，以便混合结果仍可用。
18. 作为 Kite 用户，我希望规则对所有应用一致，不写产品名专属分支，以便新安装软件获得同样体验。
19. 作为维护者，我希望最终排序在物化展示对象之前完成，以便证据、质量层、偏好同处一条比较链。
20. 作为维护者，我希望避免在完整候选上对 AppItem 多余克隆，以便有个性化时的热路径更干净。
21. 作为维护者，我希望端到端样本能分别复现「证据被最终排序覆盖」「纠错自删候选」「混输弱关联高分」，以便验收不靠肉眼。
22. 作为维护者，我希望修复顺序先证据贯穿、再纠错零值、再收紧混输高分，以便每步可用同一测试缝验收。
23. 作为维护者，我希望占位证据逐步替换为真实位置，但不把「补全所有证据字段」阻塞为本轮全量重构，以便先修可见排序错误。
24. 作为维护者，我希望性能缓存与前缀枚举上限不混进本轮正确性修复，以免范围失控。

## Implementation Decisions

- 保留 `search-quality-feedback` 已落地的统一最终排序入口与显式质量层；本轮只修证据丢失、纠错误过滤和混输高分过宽，不重开算法选型。
- 主流程调整为：验证阶段继续产出轻量候选（稳定 id、基础 MatchScore、质量层、匹配证据）；个性化与最终统一比较在轻量候选上完成；截取 Top N 之后再物化展示对象（克隆 AppItem）。禁止在最终排序前丢弃证据。
- 最终比较器统一为：质量层 → 最终分（含偏好加分）→ 匹配证据细排 → 稳定 id；无个性化路径不得再插入「名称长度 / 名称」优先于证据的规则。名称长度若仍作友好展示偏好，只能作为证据相等后的次级键。
- 个性化路径与无个性化路径共用同一证据比较键，避免空历史与有历史两套同分规则。
- 质量层继续是显式字段；不得用加分后分数反推层级。上一轮的保护层（Alias / Name Exact）与 Pin「取较大者不叠加」约束不变。
- 纠错通道：查询删除索引时返回的「删除次数」明确为查询侧生成深度，不是与原词的真实编辑距离。禁止用该值等于 0 直接跳过候选。候选是否符合纠错距离，在验证阶段用真实距离（或等价代价）判定。
- 若需要保留某种「纯精确命中不走纠错通道」的短路，必须基于「输入与词典原词相同」这一事实，而不是删除深度为 0。
- 混输高分条件收紧：整词级高分要求汉字段与拉丁段在目标字段上按顺序对齐，或由音节级混合拼音匹配器认可；各片段独立 contains、顺序不一致或位置复用的，只可进入宽召回分档，不得使用与有序混拼音相同的高分。
- 宽召回分档须低于有序对齐分档，且最终同分时证据仍可区分强弱；不要靠产品名分支实现。
- 证据字段补全本轮有边界：已明确影响同分胜负的占位（有序多词 gaps、词元起点/字段、不可映射拼音起点）应修正；允许部分罕见分支暂记未知位置（usize::MAX 或等价语义），禁止把未知写成 0/最优。
- 不改变扫描、启动、图标、Everything、托盘与空 Query 列表逻辑。
- 不引入新的外部搜索引擎、向量检索或持久化结构。

## Testing Decisions

- 好测试只断言外部可见行为：给定固定应用索引、Query 与可选个性化状态，观察最终有序 TopK 的身份与相对顺序；不断言内部函数调用次数或具体分值常量。
- **唯一主测试缝**：统一搜索入口（`search_with_personalization` / `RetrievalIndex::search_personalized`，以及无预构建索引时的 `search_system_personalized`）。证据贯穿、纠错保留、混输分档、既有偏好保护全部走这一缝。
- 仅当端到端无法隔离时，允许辅助单测：
  - 匹配证据比较器：成对比较起点/间隔/覆盖；
  - 删除索引 expand：文档化返回值语义（查询侧删除深度），并断言直接命中删除变体时深度为 0 且词典原词在结果中。
- 必测行为样本：
  1. 同分双候选：证据更优者第一，即使其稳定 id 更大；分别验证无个性化与有个性化两条路径。
  2. 上一轮偏好样本不回退：截断前偏好仍能抬升相近候选；Name Exact 仍不被强历史压过。
  3. 纠错：词典含 `chrome` 时，输入 `crome` 能召回该应用（允许非首位，但不得因通道自删而消失）。
  4. 混输强证据：顺序对齐的汉字+拼音/英文混输仍可高分进入前排。
  5. 混输弱证据：片段碰巧命中、顺序不一致的输入，不得与有序对齐同权；允许出现在更后位置。
  6. 产品名中立：不得出现针对具体软件名称的打分分支。
- prior art：沿用 `search` 模块内统一入口回归测试、`history` 分层/保护不变量测试、`tests/search_cases.json` 与 eval 基线；本轮以新增构造样本为主，避免依赖 Windows 实机截图验收算法正确性。
- 检查通过标准：`cargo test` 全绿；新增样本覆盖上述 1–5；相对既有 required eval 无显著回退。

## Out of Scope

- 取消前缀词元固定枚举上限（`MAX_PREFIX_TERMS` 类问题）——单独立项，本轮只保证不把「其他通道可能兜底」当作已完整枚举。
- `Personalization` 查询级 SQLite 全量读缓存、匹配缓冲跨查询复用等性能优化——需要运行数据，不进本轮正确性修复。
- 与 ZTools / uTools 的实机速度对比或承诺倍数。
- 重新设计 MatchScore 常量表、引入新召回通道或重做短输入策略。
- 扫描、图标、启动、Everything、托盘、安装器、UI 视觉。
- 云服务、遥测、向量检索、外部搜索栈。
- 为任何品牌或 exe 写特例。
- 签名、版本号、推送、合并与发布。

## Further Notes

- 前序：`search-experience-next` → `search-quality-feedback`（主流程统一排序、质量层、短输入/混输召回、查询偏好）。本规格是 `bd0f56f` 相对 `a07414c` 源码审查后的残留正确性修复，不推翻已修问题。
- 建议实现顺序：① 保留轻量候选并贯穿证据到最终排序（顺带消除有个性化时的重复物化）→ ② 删除纠错通道对 dist==0 的误过滤并明确距离语义 → ③ 收紧 mixed-cjk-latin 高分条件并区分有序对齐 / 宽召回。每步提交后跑主缝测试。
- 领域词汇沿用 `docs/CONTEXT.md`：AppItem、Query、MatchScore、Usage、Recency、Query History、FinalScore、明确匹配保护、Pin。本规格中的「匹配证据」「质量层级」「查询偏好」与上一轮一致；若删除深度与真实编辑距离进入长期设计，再补领域文档。
- 「相关性接近」在混输分档上应表现为可测试的有序对齐 vs 片段碰巧命中的相对顺序，而不是开放阈值。
- 本规格不打开新的工作树；实现时避免与并行搜索改动冲突。
