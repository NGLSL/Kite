Status: ready-for-agent
Type: bugfix

## Problem Statement

上一轮把应用搜索搬到了常驻 worker，结果正确性明显改善，但「异步状态、缓存依赖、展示归并」三者交界处还留着几个会真实咬人的口子，用户侧表现为：

1. **刚输入的新查询还没返回，回车却启动了上一条查询的应用。** 用户敲 `chrome`，列表还停在上一次的 Visual Studio Code，此时按 Enter（或 Alt+数字、鼠标点击），启动的是旧列表里那一行。用户会觉得「我明明换了输入，它打开错了东西」——这是启动动作，代价比排错序严重得多。
2. **改了别名，搜索结果还按旧别名走。** 把 `qa` 从应用 A 改成应用 B 之后，再搜 `qa` 仍然把 A 顶在最前（用户别名属于明确匹配保护层，会稳定排在前面）。用户会认为「设置没生效」，且只有重启或重新扫描才恢复。
3. **对有多个等价入口的应用点了「降低此结果优先级」，那一行看起来没变化。** 用户确实执行了降权、也确实持久化了，但因为同一应用的另一个扫描入口在归并时顶上来，展示行的分数又回到原值，排序与标签都不动。用户会认为「降权功能是坏的」。
4. **连打字时，旧查询仍在整批跑完验证；清空输入或隐藏窗口不会让它停下来。** 输入越快，越是把 CPU 花在已经作废的候选上。用户感受是「打字偶尔发涩」，维护者无法解释「为什么后台还在算」。
5. **按键路径并没有真正变轻。** 每按一键仍会无条件复制整份应用数组与系统入口数组，还会重复取两次索引锁；匹配计算虽然已经在后台，但提交请求这一步本身仍带着与按键次数成正比的复制开销。
6. **收尾项仍可见**：compact 一类的派生字段命中没有把位置映射回原文，诊断与同分细排拿到的是紧凑文本坐标；真实名称里的超长词元进不了一阶纠错；查询级日志仍然直接进同步日志写入。

用户会感到：**单个函数测试都过了，实际操作仍偶发不对**——因为问题不在某个函数，而在几次异步事件之间的时序和归并关系。

## Solution

在**不更换搜索架构、不重做归并框架、不引入通用缓存系统**的前提下，把三个交界处接稳，并把按键路径与取消粒度的欠账收掉：

```text
输入新 Query
   ↓
提交后台请求（推进查询代际）——旧结果仍可显示，但不再具备“可启动”资格
   ↓
后台结果返回 → 核对 [查询代际 + 查询文本 + 索引代际 + 偏好版本] → 合并落地
   ↓
结果可用（恢复可启动资格）→ Enter / Alt+数字 / 点击 只对“结果代际有效”的列表生效
```

```text
别名增删改
   ↓
同时失效：基础候选缓存 + 正在执行的旧请求（走同一套代际/失效入口）
   ↓
不得出现“旧任务跑完再把旧别名结果写回当前缓存”
```

```text
等价入口组（同一安装、同一启动动作、已确认可合并）
   ↓
降权状态按“展示组”统一解释：组内成员一致受影响，且不重复累加
   ↓
保留明确匹配保护；不按软件名称扩大降权范围；不因此撤销归并、不恢复两行微信
```

具体体验：

- **不会开错应用**：新查询提交后，旧列表可以继续显示（避免闪空），但启动动作必须先确认列表属于当前查询。
- **设置立刻生效**：改完别名，下一次同样的输入就按新别名排。
- **降权看得见**：对重复入口的应用降权，该行确实后移；恢复后回到原顺序。
- **算得动、停得快**：候选验证按小批次检查取消；清空输入、隐藏窗口也通知 worker 停止当前任务；matcher 与工作缓冲跨查询复用；按键路径不再全量克隆。
- **位置与日志收尾**：compact 命中位置映射回原文（或明确记为未知，不假装最优）；真实名称的长词元进入一阶纠错；查询级日志可关。

## User Stories

1. 作为 Kite 用户，我希望在新查询的结果还没回来时按 Enter 不会启动上一条查询的应用，以便我不会开错程序。
2. 作为 Kite 用户，我希望 Alt+数字在结果未就绪期间不会启动过期行，以便快速启动不会被时序破坏。
3. 作为 Kite 用户，我希望鼠标点击结果行的启动判定与键盘一致，以便三个启动入口共享同一套有效性规则。
4. 作为 Kite 用户，我希望结果未就绪期间列表可以保留旧内容而不是闪空，以便视觉上不跳动。
5. 作为 Kite 用户，我希望「列表可启动」的条件是明确的、可测试的代际关系，而不是「列表非空」。
6. 作为 Kite 用户，我希望固定项切换、清空历史、降权恢复等会改变排序的操作都走同一条请求失效入口，以便它们不会与在途搜索互相覆盖。
7. 作为 Kite 用户，我希望发生在途搜索期间的操作不会把刚更新的顺序又改回旧顺序。
8. 作为 Kite 用户，我希望新增、修改、删除别名之后，同样的输入立刻按新别名排序，以便设置看起来是即时生效的。
9. 作为 Kite 用户，我希望别名改动会同时让在途请求作废，以便旧结果不会随后覆盖新别名结果。
10. 作为 Kite 用户，我希望别名改动会同时让基础候选缓存作废，以便不会命中「用旧别名算出来的候选」。
11. 作为 Kite 用户，我希望缓存的失效不只清空数据，还要防止旧任务完成后把旧结果写回，以便缓存不会自我污染。
12. 作为 Kite 用户，我希望别名之外的偏好（历史、配对、固定、降权）变化也走同一套失效/重放规则，以便不存在「有些偏好即时、有些不即时」的错觉。
13. 作为 Kite 用户，我希望对有多个等价入口的应用执行「降低此结果优先级」后，那一行确实后移，以便降权是可感知的。
14. 作为 Kite 用户，我希望同一展示组内的成员一致受到该降权影响，以便组内另一个入口不会把它抵消。
15. 作为 Kite 用户，我希望同组降权不做重复累加，以便一次降权不会变成过度惩罚。
16. 作为 Kite 用户，我希望降权仍然可以被恢复，以便误操作不留下永久后果。
17. 作为 Kite 用户，我希望降权不越过明确匹配保护，以便「我就是要搜这个名字」仍然有效。
18. 作为 Kite 用户，我希望降权不删除索引项、不改启动目标，以便应用仍然能被正确启动。
19. 作为 Kite 用户，我希望降权不按软件名称扩大范围，以便不影响同名的无关条目。
20. 作为 Kite 用户，我希望连打字时旧查询的候选验证能中途停下，以便我的新输入更快拿到结果。
21. 作为 Kite 用户，我希望清空输入框时后台也停止当前任务，以便「清空」在计算意义上也是清空。
22. 作为 Kite 用户，我希望隐藏窗口时后台也停止当前任务，以便不用的时候不占 CPU。
23. 作为 Kite 用户，我希望取消后的任务不产生任何结果、不写缓存、不回调，以便取消是彻底的。
24. 作为 Kite 用户，我希望匹配器与工作缓冲在多次查询之间复用，以便连续输入时少做重复初始化。
25. 作为 Kite 用户，我希望按键提交搜索这一步不再复制整份应用与系统入口数组，以便按键路径真正变轻。
26. 作为 Kite 用户，我希望索引状态只被读取一次就拿到自洽的一份快照，以便不会出现两次加锁之间状态不一致。
27. 作为 Kite 用户，我希望 compact 一类派生字段的命中位置映射回原文（映射不了就明确记为未知），以便同分细排与诊断拿到真实位置。
28. 作为 Kite 用户，我希望真实名称里较长的词元也能进入一阶纠错，以便长英文名打错一个字母仍能被找到。
29. 作为 Kite 用户，我希望纠错范围仍然受限，以便不因放宽长词而重新带来内存与误召回。
30. 作为维护者，我希望查询级日志可以关闭，以便按键路径上不再有同步日志写入。
31. 作为维护者，我希望用测试屏障固定「旧任务正在验证」这一时刻，而不是靠调度碰运气，以便取消测试是确定性的。
32. 作为维护者，我希望四个关键时序场景被固定成回归测试：延迟后台结果后快速输入并启动、缓存命中后修改别名、对有重复入口的应用降权、计算中清空查询。
33. 作为维护者，我希望文档与代码注释同步更新，以便不再出现「注释说只缓存无偏好查询、代码已经每次重放偏好」这类漂移。
34. 作为维护者，我希望本轮不引入新框架、新外部依赖或第二套缓存系统，以便收口而不是扩张。

## Implementation Decisions

- **不重开搜索架构**：保留统一最终排序入口、质量层、明确匹配保护、启动组归并、常驻单 worker 与最新请求覆盖。本轮只收紧异步边界、缓存依赖与展示归并。
- **结果代际（新增领域概念）**：已展示的列表携带「结果代际」。新查询提交后，列表可继续显示，但失去可启动资格；只有与当前查询/索引代际一致的落地结果才恢复资格。所有启动入口（Enter、Alt+数字、鼠标点击行）共用同一有效性判定，判定放在启动动作入口处，而不是分散在三个调用点。
- **单一失效入口**：会改变结果顺序或匹配输入的操作（Query 变化、固定切换、清空历史、降权/恢复、别名增删改、索引重建、文件模式切换）统一走同一个「请求失效 + 重新提交」入口。禁止再出现绕过该入口的同步搜索调用；空 Query 的固定+最近同步路径保持不变。
- **偏好版本纳入缓存依赖**：基础候选缓存的键或失效条件必须包含「影响基础候选的输入」，至少覆盖别名目标集合（用户别名直接决定明确匹配保护层的命中）。别名增删改时：清缓存 + 推进失效代际，使在途任务完成后不再写回。
- **缓存语义固定为「个性化前候选」**：缓存存的是召回+验证后、个性化/归并/截断前的轻量候选；个性化每次都按最新偏好重放。**不缓存截断后的 TopN 当全集**。更新现有注释与工单说明，使其与实现一致。
- **降权按展示组统一解释**：归并时，降权状态以「已确认等价的展示组」为单位生效——组内成员一致受该组降权影响，不重复累加；展示代表的选择与降权解释共用同一份等价组信息，不新增第二套等价判定。
- **取消回调贯穿验证循环**：候选验证接收取消检查，并按小批次（而非每个候选）查询取消状态；已有的阶段边界检查（召回后/验证后/排序前）保留。取消语义不变：取消即不返回部分结果、不回调、不写缓存。
- **worker 增加显式取消入口**：清空 Query、隐藏窗口等「界面不再需要结果」的场景，除清理界面状态外，还要通知 worker 停止当前任务（推进请求失效即可，不需要 kill 线程）。
- **搜索请求的索引来源收敛为一个概念**：请求携带「预建索引」这一首选来源，仅在冷启动无预建索引时才需要后备数组；按键路径上不得无条件克隆完整数组；索引状态一次读取拿到自洽快照。是否引入一个小枚举表达「预建索引 / 后备快照」交由实现者判断，但不新增缓存层。
- **matcher 与工作缓冲跨查询复用**：worker 持有匹配器与工作缓冲，查询只更新 pattern 与解析结果。这是复用，不是新抽象。
- **位置映射收尾**：compact 等派生字段的命中位置在可映射时映射回原始展示文本（含空白在内的真实字符下标），不可映射时记为未知，不得写成 0 或最优起点；未知位置不得战胜真实前缀位置。
- **纠错范围收尾**：真实名称中的较长词元进入一阶删除变体，不恢复全量派生词、不扩大距离 2 的生成集合；已知的内存水位约束（删除索引键数）不得回退。
- **日志开关**：查询级日志（结果就绪/过期等）改为可关闭；默认仍保留可诊断性，但不得在按键路径上产生同步文件写入。
- **诊断仍只读**：诊断产物必须复用同一条排序链，不得分叉排序逻辑，也不得为诊断复制一份物化逻辑。
- 不改扫描、启动、图标、Everything 文件搜索协议、托盘与空 Query 列表语义；不引入新的外部搜索引擎、任务框架或缓存系统。

## Testing Decisions

- 好测试只断言**外部可见行为**：给定固定应用索引、Query、可选偏好/别名状态与（服务缝）代际，观察最终 TopK 的身份与顺序、启动动作是否被拒绝、取消是否产生结果；不断言内部调用次数或具体分值常量。
- **主测试缝（搜索正确性，优先）**：统一最终排序入口（`search_with_personalization` / `RetrievalIndex::search_personalized`）。降权按组解释、位置映射、纠错范围都走此缝。
- **服务缝（后台调度）**：常驻 worker 的提交/取消/缓存复用。用测试屏障（而非 sleep 赌调度）固定「旧任务正在验证」的时刻，再提交新任务，断言旧任务被取消且不回调、不写缓存。
- **UI 缝（时序与启动）**：沿用现有 UI 测试支撑（构造 State 字面量 + 消息更新入口），断言「新查询提交后、结果返回前」启动动作被拒绝；这是唯一需要 UI 缝的场景，其余不进 UI。
- **辅助单测**：缓存失效（别名变更路径）、map 位置函数在含空白文本上的返回、诊断结构字段完整性（只读）。
- 必测行为样本（本轮验收项，逐条固定）：
  1. **延迟后台结果后快速输入并启动**：旧查询结果仍在列表中时提交新查询并触发起动，不得启动旧结果；新结果落地后启动正常。
  2. **缓存命中后修改别名**：先让某别名查询进入缓存，改别名指向另一目标，再次同样输入，结果按新别名；且不出现旧任务回写。
  3. **对有重复入口的应用降权**：同一展示组内等基础分成员存在时，降权后该展示行确实后移；恢复后回到原序；启动目标不变。
  4. **计算中清空查询**：清空后旧任务不再产生任何结果与回调。
  5. **位置映射**：含空白的展示名上，首字母/紧凑类命中映射到真实字符下标；不可映射记为未知且不战胜真实前缀。
  6. **长词元一阶纠错**：13–18 字符的真实名称词元打错一个字母仍可召回，且删除索引规模不显著回退。
  7. **不回退项**：统一最终排序、质量层、明确匹配保护、Pin 语义、既有偏好样本全部保持；`cargo test` 全绿。
- prior art：沿用 `search` 模块统一入口回归测试与 `history` 的保护/分层不变量测试；服务缝参考既有文件查询 generation 模式的测试风格；UI 缝参考现有键盘与 Alt+数字测试。以新增构造样本为主，不依赖 Windows 实机截图验收算法正确性。
- 真机冒烟（非算法验收门槛）：连续输入 + 回车、改别名后重搜、对重复入口应用降权、计算中清空，各做一次。

## Out of Scope

- 通用「带偏好查询的缓存加速」（若要复用缓存，应缓存截断前的轻量候选与证据再应用新偏好——本轮不为它建系统）。
- 更换搜索算法、换 matcher、引入向量检索或新的拼写引擎。
- 重做启动组归并框架；撤销归并；恢复同一应用的两行展示（如两行微信）。
- 压缩全部搜索字段换取内存；重新追求最低驻留内存。
- 恢复全量 SymSpell 派生词生成；放宽删除索引距离与长度上限。
- compact 独立纠错的重新引入（此前的收缩是已接受的取舍，不再包装成「完全无损」）。
- 历史长期内存快照、诊断可视化产品面板、负反馈学习模型、云端同步。
- 安装器（NSIS）与签名/发布流程的规格化——本规格只涉及搜索服务与 UI 时序。
- 为任何品牌或 exe 名称写特例。

## Further Notes

- **本规格的输入**：一份针对 `dev` 上 `6e19b99` 的源码审查（覆盖 `08e516b` 之后一轮的内存优化、参考项目能力补齐、常驻线程、个性化与数据库迁移），以及对该审查逐条的代码复核。审查方向被判定为正确、应当保留；本规格只收口交界问题，不推翻任何已完成的优化。
- **已核对为「不必返工」的点（勿重复要求实现）**：
  - 拼音首字母命中的位置映射**已修**（首字母串字节偏移 → 原始展示文本字符下标，含空白）；
  - 主路径**已统一**为轻量候选（RankedHit）一条排序链，`SearchResult` 的个性化入口只服务于工具/测试路径，不再是主路径风险；
