# 02: 已展示结果携带「可启动代际」

**Status:** resolved
**Blocked by:** 01（统一结果变更的失效与重提入口）
**Type:** bugfix

**What to build:** 用户敲下新查询、结果还没回来时，列表可以继续显示上一次的内容（不闪空、不跳动），但此时无论按 Enter、按 Alt+数字，还是用鼠标点那一行，都不会启动旧列表里的应用。新结果落地后，三个启动入口一起恢复正常。

- [x] 已展示列表携带「结果代际」，与提交时的查询代际、查询文本、索引代际绑定 —— 实现取更简形式：`State::results_stale` 陈旧标志（列表本就滞后于最新提交，代际数值不承载额外信息；审查亦建议如此）
- [x] 新查询提交后，列表失去可启动资格，但显示内容保留
- [x] Enter、Alt+数字、鼠标点击行三个入口共用同一份有效性判定，判定位于启动动作入口处，不分散在三处（`launch_selected` 单点守卫）
- [x] 结果未就绪期间触发启动被拒绝，且不产生任何启动副作用（不启动进程、不改历史、不动使用次数）
- [x] 新结果落地后，同一动作正常启动
- [x] UI 缝回归：固定「提交新查询 → 旧结果仍在列表 → 立即启动」这一时序，断言不启动旧行（`stale_results_cannot_be_launched_until_current_query_lands`）

## Notes

- 这是本轮唯一需要 UI 缝的场景，其余验收不进 UI 层。
- 「可启动」的条件必须是明确的代际关系，不能是「列表非空」。
- 拒绝启动时不要给用户弹错误提示，静默拒绝即可。
- 鼠标点击与键盘必须同规则，否则会出现「键盘拒绝、鼠标照旧」的错觉。

## Answer（提交 279e4b8）

- `State.results_stale`：提交新查询后置位、结果由 `apply_app_search_ready` 落地后清除；
  旧列表继续显示（不闪空），但**立即失去可启动资格**。
- 唯一的判定入口 `State::results_are_launchable()`（`src/ui/results.rs`），
  Enter、Alt+数字、鼠标点击共用这一个判定，不各写一份。
- 拒绝启动是静默的，不弹提示。回归测试
  `stale_results_cannot_be_launched_until_current_query_lands`（`src/ui/results.rs`），
  覆盖「旧列表仍显示 → 拒绝启动 → 结果落地 → 恢复启动」三段。
