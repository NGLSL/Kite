# 01: 统一结果变更的失效与重提入口

**Status:** resolved
**Blocked by:** None (can start immediately)
**Type:** prefactor

**What to build:** 用户在做任何会改变结果顺序或匹配输入的操作之后——固定／取消固定、清空历史、降权／恢复优先级、增删改别名、重建索引、切换文件模式——列表不会再出现「我刚改完，它又跳回旧顺序」。所有这类操作走同一条「请求失效 + 重新提交」通道，正在跑的后台搜索不会再把自己的旧结果盖回来。

- [x] Query 变化、固定项切换、清空历史、降权／恢复、别名增删改、索引重建、文件模式切换全部汇入同一个「请求失效 + 重新提交」入口（本轮补上「别名增删改」这条缺口，其余原先已在 `refresh_results` 上）
- [x] 该入口推进请求失效代际，使在途任务完成后其结果被丢弃
- [x] 不存在绕过该入口的同步搜索旁路；空 Query 的「固定 + 最近」同步路径保持原语义，不被卷入
- [x] 在途搜索期间执行上述任一操作，最终顺序以该操作为准，不被旧任务覆盖（依托既有代际丢弃）
- [x] 统一排序主缝新增回归：操作发生在在途搜索期间，落地顺序正确 —— **部分**：本轮以 UI 缝 `alias_change_invalidates_base_cache_and_resubmits` 覆盖「操作使在途请求作废」；「旧任务不覆盖新顺序」由既有代际丢弃保证，未新增独立主缝用例
- [x] 顺手清掉本轮确认「无生产调用点」的判断（`prefs_is_empty` 及其测试已删）

## Notes

- 本票是 prefactor：本身不引入新的用户可见功能，但它让 02／03／06 都能落成小改动。这是「先让改动变容易，再做容易的改动」。
- 复用既有代际机制，不新建框架、不新建缓存层。
- 实现完成后，若 02 与其合并更自然，可由实现者判断，但验收项不得丢失。

## Answer（提交 279e4b8）

已按 prefactor 落地，未新建框架或第二套缓存机制：

- `BaseHitCache` 补上统一的失效入口：`invalidate()`（推代际）、`epoch()`、`insert_if_epoch(epoch, index_gen, query_norm, hits)`。
- 写回带代际校验：失效之后在途搜索跑完也写不回去。回归测试
  `invalidate_rejects_writeback_from_in_flight_search`（`src/search/service.rs`）。
- 索引重建推进索引进代际并清空缓存，与别名失效走同一个入口——02／03／06 因此都只是小改动。

未验证项：无新增 UI 行为，真机冒烟随 02 一起看。
