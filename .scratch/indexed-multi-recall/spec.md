# 索引驱动的多路搜索内核

## Problem Statement

Kite 已有名称精确/前缀/片段、英文分词与缩写、基础拼音、Alias、模糊匹配及分层排序。先前记录的 `ter`、`todo`、`kz`、`power`、`visual code`、`ndm`、`雷蛇` 等案例已解决，本规格只将它们作为回归保护。当前非空 Query 仍逐项遍历 AppItem，对每项组合执行文本匹配，并仅在前面所有匹配都失败时尝试编辑距离。现有 Kite 设置、Windows 设置页和系统工具另走查询时的独立匹配与图标生成，再同应用结果合并；应用结果先截断，内置项也有单独的截断和分数。查询时还会再做规范化、对象克隆、历史读取，并可能同步等待可选文件搜索。没有面向统一搜索字段的候选索引，也不能通用地覆盖同一次输入中的全拼/简拼/汉字/英文混输及更广泛的跳字输入。

用户希望面对同一批已安装软件和现有系统入口，用更短、更不完整的 Query 更全、更准、更快地找到正确候选。弱相关结果不能阻断其他召回通道；增加结果数量本身不是成功指标。本轮不增加插件、功能指令或新的结果来源。

## Solution

在现有 AppIndex 的每个可搜索快照中构建只读 RetrievalIndex，让已安装 AppItem 与现有 Kite 设置、Windows 设置页、系统工具共用搜索字段、内部整数 ID 和匹配证据。Query 只解析一次；英文、拼音、汉字及其混合解释可以同时参与 FST 词典与倒排、字符 2/3-gram 倒排、字符位图与有序验证、SymSpell 删除索引、音节级混合拼音等通道。各通道分别召回，候选取并集，再按命中字段、位置、连续性、间隔和纠错代价验证与统一排序。既有 Alias、明确匹配保护、Pin、Query History、Usage、Recency 继续决定相关候选间的偏好；`nucleo-matcher` 只负责适用候选的字符对齐质量，不替代召回引擎，也不否决纠错或拼音通道的有效证据。

验收以同一批已索引条目、现有固定 Query 集、未专门适配的新名称/输入变形和不做索引剪枝的参考匹配器为准，证明合理候选没有被提前漏掉，同时提升前排相关性。记录构建耗时、索引内存、候选量、召回/排序耗时、首批本地结果延迟和结果噪声；在真实 Windows 列表中核对可见结果与历史偏好。慢数据源和图标准备不能延迟本地搜索结果。

## User Stories

1. 作为 Kite 用户，我希望输入应用名或 Alias 的完整词时直接找到目标，以便快速启动。
2. 作为 Kite 用户，我希望输入词前缀时找到相应应用，以便不用打完整名称。
3. 作为 Kite 用户，我希望输入多个词时只看到满足这些词解释的相关应用，以便缩小结果范围。
4. 作为 Kite 用户，我希望多词可以分别命中名称、显示名、英文缩写或拼音字段，以便不必猜测索引如何分词。
5. 作为 Kite 用户，我希望输入名称中间的连续片段也能找到应用，以便只记得名字的一部分时仍可搜索。
6. 作为 Kite 用户，我希望省略若干字符或按顺序跳字输入时仍能召回目标，以便随手输入也能找到新应用。
7. 作为 Kite 用户，我希望错拼中的漏字、错字和相邻字符交换能找到真实安装的应用，以便不必重输整个词。
8. 作为 Kite 用户，我希望很短的 Query 不触发大量无关纠错，以便首屏保持清晰。
9. 作为 Kite 用户，我希望同一 Query 可交替使用汉字、全拼、简拼和英文，以便输入方式自然切换。
10. 作为 Kite 用户，我希望多音字采用正确读音时也能找到应用，以便不受索引时选定的一条读音限制。
11. 作为 Kite 用户，我希望某个弱匹配已出现时，其他通道仍有机会找到更相关目标，以便首屏不被噪声占满。
12. 作为 Kite 用户，我希望精确匹配和用户 Alias 继续优先于弱模糊或纠错结果，以便排序可预测。
13. 作为 Kite 用户，我希望自己的 Pin、Query History 和使用偏好继续在相关候选间生效，以便升级后不丢个人习惯。
14. 作为 Kite 用户，我希望安装、卸载或修改入口后的新快照和搜索结果同步更新，以便不会搜到旧 target 或漏掉新应用。
15. 作为 Kite 用户，我希望快速扫描和后台完整扫描的每次发布都可搜索，以便索引重建期间输入仍流畅。
16. 作为 Kite 用户，我希望已有应用与 Kite 设置、Windows 设置页、系统工具按同一匹配质量比较，以便前排不受来源合并顺序影响。
17. 作为 Kite 用户，我希望滚动查看更多结果时仍可能看到相关应用，以便候选不会在评分前被任意截掉。
18. 作为维护者，我希望新增应用和随机变形 Query 也能与全量参考匹配结果对照，以便发现预过滤导致的漏召回。
19. 作为维护者，我希望分别观察每条通道的候选量、验证通过量和耗时，以便知道速度和噪声来自哪里。
20. 作为维护者，我希望看到索引构建时间、内存增量和查询延迟随 AppItem 数增长的变化，以便判断多路索引的实际收益。
21. 作为 Kite 用户，我希望一串字母可同时按英文缩写、词片段或拼音解释，以便不用猜测应选哪种输入方式。
22. 作为 Kite 用户，我希望记得名称中几个不相邻的词时仍能按顺序找到目标，以便不必补齐中间单词。
23. 作为 Kite 用户，我希望每个短 Query 的使用偏好逐渐影响相近候选的顺序，以便常用目标更靠前且完整名称的明确匹配仍受保护。
24. 作为 Kite 用户，我希望先看到本地应用和系统入口，再看到可能较慢的可选文件结果，以便输入时不被文件 IPC 拖慢。
25. 作为 Kite 用户，我希望图标尚未准备好时仍先看到正确的名称和目标，以便搜索响应不等待图标提取或校验。
26. 作为 Kite 用户，我希望网页搜索和 Everything 的既有开关、入口及结果语义保持稳定，以便搜索内核升级不改变其他功能。

## Implementation Decisions

- 只升级已有应用与系统入口的搜索内核；AppItem 的稳定 ID、已验证 target、扫描来源与启动契约继续沿用。现有 Kite 设置、Windows 设置页、系统工具形成只读可搜索条目，与已安装应用共享搜索字段和候选评分，不新增系统命令或结果来源。内部使用快照局部整数 ID，并保留到稳定条目 ID 的映射；整数 ID 不作为持久化身份。每个搜索字段标注所属条目与字段类型，名称、显示名、规范化/紧凑形式、词元、英文缩写、明确 Alias、系统入口已有关键词和拼音读音按各通道需要入索引；用户 Alias 可作为随配置变更重建的只读叠层，但须映射到同一稳定条目 ID 和统一证据/排序流程，不能退回逐项扫全部 AppItem。不把用户 Query 或未索引的外部词典变成可启动 target。
- RetrievalIndex 与可搜索条目组成同代只读快照；快速扫描、UWP 合并、后台完整扫描或入口监听导致搜索字段变化时，先构建新索引再发布，不允许查询看到新条目配旧倒排。固定系统入口可在快照构建时合入；仅图标变化不必重建词典。索引构建在后台执行；发布与查询不持有覆盖完整匹配过程的全局可变锁。
- 以现有“可搜索快照 → Query → 最终可见结果”作为主要集成缝。空 Query 的 Pin/Recency 行为保持，非空 Query 的应用和已有系统入口先统一召回与评分，再与既有网页/可选文件来源按原语义合并；不能沿用“先截断应用、再追加并预置系统分数”的前排决定方式。既有 `matched_by` 对外可保留一个主要来源，内部须保留多通道证据及命中字段、字符/词位置、连续段、间隔与纠错代价，供 MatchScore 计算和诊断使用。
- FST 词典将规范化词元映射到倒排表地址或词元 ID；倒排表使用排序、去重的内部 ID 列表。FST 在快照构建时整体生成，支持词精确和前缀枚举，不尝试原地修改。一个 Query 词的不同合法解释先取并集，多个 Query 词再按最短倒排优先求交；多词的实际字段、词序和边界最终逐候选验证。多字段解释不得因过早跨字段求交而丢失合法候选。
- 连续中段输入用按 Unicode 字符切分的 bigram/trigram 倒排。短片段优先 bigram，较长片段优先 trigram；先查询稀有 gram 缩小候选，再核对全部必要 gram 和原字符串中的连续位置。倒排使用适合稀疏集合的排序列表，不给每个 gram 分配全量位图。
- 跳字输入用搜索字段级字符位图做必要条件预过滤，再检查字符顺序、重复次数、跨度和词边界。位图中的“含有字符”不能视为命中，也不能在 Query 重复字符时替代计数验证。短 Query 或高频字符几乎不具选择性时，按成本模型选择更适合的精确/前缀通道或保守验证，不对全集无条件运行昂贵对齐。
- SymSpell 删除索引仅从已索引应用的真实词元和可信 Alias 生成；Query 及其删除变体找到原词元后，再用与既有模糊语义一致的编辑距离验证并映射到 AppItem。编辑距离随 Unicode 字符数限制为 0/1/2，不导入普通英语大词典；处理漏字、替换和相邻交换，控制长词删除变体的构建与存储成本。纠错通道独立于原 Query 的 gram/字符交集，不能被其他通道的必要条件误删。
- 中文通道采用 `ib-pinyin` 的音节级混合匹配能力，允许同一输入中全拼、简拼、汉字和英文混用，并覆盖多音字。预过滤要把允许的读音和原文字符都纳入必要条件；不能用仅一条全拼加一条首字母的位图误删正确候选。无法证明某种混合 Query 的位图条件安全时，使用更宽的锚点或保守候选集合，再交给音节匹配器验证；不预生成全拼/简拼/多音字的笛卡尔积。
- 对适用的非连续候选复用 `nucleo-matcher` 的匹配缓冲与对齐分数。精确、词前缀、Alias、纠错距离及混合拼音拥有各自的验证和质量证据；`nucleo-matcher` 对原 Query 不命中不能删除其他通道已经验证成立的结果。同一条目跨字段、跨通道的证据先合并，再基于字段可信度、命中位置、连续性、间隔和纠错代价形成 MatchScore；弱片段与错拼可以保留在结果中，但不能仅因通道多或结果多而占据前排。已有系统入口与应用使用同一质量层级和明确匹配保护，来源只在有明确语义时参与同质量候选的处理，不给全部系统入口固定置顶。
- Query 在本地搜索、系统入口、用户 Alias 和排序之间只规范化、解析一次；一段拉丁字母可同时按英文、缩写和拼音解释，不能按字符类型排他选择。按 Query 类型、词长、倒排大小及预算触发相关通道，但不得以“已有普通结果”为停止条件。各通道候选合并去重后竞争排名；不能先按 FST 字典序或扫描顺序 `take(N)` 再排序。候选过多时用可解释的成本/上界剪枝或分批扩展，保证高质量证据与最终 Top K 的正确性；记录预算触发与被推迟的扩展，不能静默丢弃。
- Query History 继续记录规范化 Query 与稳定条目 ID 的选择关系，并与 Pin、Usage、Recency 一起在同层或相近质量候选间形成 FinalScore。对短 Query 的重复选择可以逐渐改变前排；完整名称、用户 Alias 等明确匹配仍受保护，不能让历史把无关弱匹配抬到明确匹配之前。最终 Top K 应按统一质量层级和层内分数排序，避免最后一次单纯按数值分数重排冲掉保护。历史数据结构和用户开关沿用现有实现。
- 在候选级保留 ID 和借用的搜索字段，复用查询解析结果与匹配缓冲；排序前避免为所有可能候选克隆完整 AppItem 或反复做拼音/分词、图标与路径计算。仅在最终需要展示时物化结果对象。保持当前最多 200 条结果上限，但截断发生在所有本地候选的验证、统一基础评分和相关个性化竞争之后。搜索组件不得改变用户原始 Query、名称、Alias、target 或 Windows 启动参数。
- 本地应用与系统入口应先独立于慢数据源完成并展示；可选 Everything 查询若较慢，异步合并其结果并以 Query 代际丢弃过期响应。已有系统入口的图标路径应在快照准备或异步显示阶段取得，不能在每次按键的候选匹配路径同步提取/校验图标。这里只调整调用时机和结果合并，不重写 Everything、图标提取或缓存规则，也不新增文件结果来源。

## Testing Decisions

- 主要测试缝为“给定一份可控的已安装应用与现有系统入口快照及 Query → 返回稳定条目 ID、顺序和主要匹配来源”，不把 FST 内部节点、位图块数或精确分数常量当作行为断言。索引快照更新另以“入口变化 → 新快照 → 相同 Query 的结果”验证；可选慢结果用“快速本地结果 → 同代文件结果合并/旧代响应丢弃”验证。优先复用当前固定搜索评估、系统入口测试、matcher/ranker 回归和搜索热路径基准。
- 建立不做索引剪枝的参考匹配器，使用相同规范化、字段和各通道的最终验证语义。对固定 fixture、不同规模的生成条目、未专门适配的新名称及随机 Query 变形，逐通道比较应命中的稳定 ID 集合；要求无漏召回，允许预过滤产生随后被验证剔除的假阳性。额外核对并集后的 Top K 与不剪枝参考排序一致，特别覆盖 FST 多词解释、重复字符、Unicode gram、错拼与 gram 冲突、多音字及中英混输。
- 保留现有已解决样本作为回归，不把通过它们算作本轮新增能力。新样本按输入类别而非产品名组织：中段片段、不相邻词、跳字/有序缩写、插入/删除/替换/相邻交换、英文/拼音同串多解释、混合全拼/简拼/汉字/英文、非默认多音字、短 Query 噪声以及应用与系统入口同词竞争。核对命中位置、连续性、间隔和纠错代价带来的前排顺序；验证 Alias、Pin、Query History、友好入口优先、网页搜索槽位和 Everything 开关没有退化。
- 比较改动前后相同机器、同一批应用与系统入口、相同 Query 的 Top1、Recall@5、MRR、无关首屏结果数和每通道召回/通过候选数；新增能力使用独立于旧案例的未适配输入集，不能以总结果数上升替代质量指标。分别测量索引构建时间、内存增量、召回耗时、候选验证耗时、最终排序耗时、本地结果首帧和完整可选结果端到端 P50/P95；覆盖现有约 80 和 2,000 条合成规模，并补真实 Windows 快照。目标是在大索引上的非连续/纠错 Query 显著减少全量对齐和编辑距离次数，同时精确/前缀 Query 不出现可感知延迟回退；性能结论附实际数值，不仅凭编译通过。
- 运行相关 Rust 回归与 release 基准；Windows 实机检查快扫、完整快照、入口变化后同一 Query 的可见结果和响应。记录尚未实测的项目，不把静态检查等同运行验收。

## Out of Scope

- 重做已经解决的单个应用案例、按品牌或产品名增加专属匹配分支。
- 插件、插件接口、功能指令、新的系统命令、新的搜索结果来源，或靠增加结果数量证明搜索改善。
- 改动扫描来源、图标提取算法、Windows 启动、文件搜索/Everything 索引、网页搜索语义或 Iced 界面视觉；仅允许为避免阻塞本地搜索而调整已有数据源和图标的调用时机。
- 把云端词典、普通英语大词典、AI/向量/Embedding/LLM 搜索、Tantivy、SQLite FTS 或额外后台服务加入应用召回。
- 将内部整数 ID 持久化，或让纠错自动改写用户 Query、Alias 与启动 target。
- 发布、部署、签名、合并或推送。

## Further Notes

- 当前搜索评估样本和基准已经存在；本轮应先记录当前代码的基线，再用同一套样本比较新旧索引，并另建未适配输入集评估泛化。现有前 10 个搜索体验任务已经标记完成或 done，应作为依赖事实和回归来源，而非新任务列表。
- 当前界面查询链路先调用应用搜索并截断至最多 200 条，再生成/追加现有系统入口、读取历史并重新排序；现有系统入口在按键查询中构造 AppItem 且调用图标缓存，可选 Everything 文件 IPC 也在结果刷新中同步调用。统一排序和首批本地结果延迟必须在这条真实链路上验收，不能仅拿独立 matcher 微基准代表完整体验。
- FST 的整数值与构建后不可变特性见 [fst Map 文档](https://docs.rs/fst/latest/fst/map/struct.Map.html)；gram 倒排需要后验验证见 [Stanford IR Book](https://nlp.stanford.edu/IR-book/html/htmledition/k-gram-indexes-for-wildcard-queries-1.html)；字符集合操作见 [fixedbitset 文档](https://docs.rs/fixedbitset/latest/fixedbitset/struct.FixedBitSet.html)。
- `ib-pinyin` 官方示例支持 `pysousuoeve` 命中“拼音搜索Everything”，并声明支持混合拼音与多音字，见 [ib-pinyin 文档](https://docs.rs/ib-pinyin/latest/ib_pinyin/)；[nucleo-matcher 文档](https://docs.rs/nucleo-matcher/latest/nucleo_matcher/)说明其匹配器复用和使用边界。SymSpell 的删除变体思想见 [项目 README](https://github.com/wolfgarbe/symspell)。这些是组件选型依据，最终依赖版本、许可、二进制体积和 Windows 构建仍应在实现时核对。
