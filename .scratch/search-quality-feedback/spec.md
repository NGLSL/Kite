Status: ready-for-agent
Type: enhancement

## Problem Statement

Kite 已有多路召回、混合拼音、纠错和历史分层，但用户仍会感到「输入很短时有时搜不到」、「同样的片段命中有时排得奇怪」、「纠正过一次排序后下次又回到原样」。

根因不在缺少新算法，而在现有引擎的三处不一致：

1. **短输入覆盖不统一。** 一个字符主要走前缀；拼音首字母中间匹配至少要两个字符；FST 前缀只枚举有限词元。结果是同类意图在不同字段上表现不同，正确候选有时进不了最终列表。
2. **同一种匹配缺少好坏证据。** 验证阶段大量分支通过固定分常量取最优，连续段位置、词边界、覆盖比例、编辑距离等证据没有参与最终比较；多路通道命中同一段内容时还可能重复叠加成虚高分。
3. **偏好反馈晚且会被抹掉。** 检索内核先按基础分截断到 Top K，UI 再读历史、加分、重排；被截断的候选永远失去竞争机会。质量层在历史加分后建立，随后纯数值 `rerank` 又只比最终分数，保护规则被覆盖。用户对某 Query 的选择记录难以稳定改变下次顺序。

用户需要的是：短输入也能稳定找回目标；排序依据可解释且可复现；纠正过一次排序后下次立刻有感，同时完整名称和明确别名仍受保护。

## Solution

在保留 Kite 现有多路召回、索引和历史模型的前提下，借鉴 ZTools 的三条可验证原则：**覆盖一致、排序有依据、选择有反馈**，并修通主流程：

```text
多路召回
    ↓
候选验证，保留 ID 与匹配证据
    ↓
读取查询偏好、历史和固定信息
    ↓
统一计算质量与偏好
    ↓
一次最终排序、截取 Top N
    ↓
物化展示对象
```

具体体验：

- **一个字符**：名称内部字符、英文词首、拼音首字母任意位置均可命中；不做拼写纠错。
- **两到三个字符**：支持连续片段和有依据的缩写；非连续匹配须经顺序、重复次数和间隔验证。
- **较长输入**：继续保留多词、混合拼音、跳字和纠错通道。
- **同是片段命中**：完整词、词边界、连续且紧凑的匹配更靠前；偶然词中片段和高代价纠错靠后。质量层是显式字段，不靠加分后数值区间反推。
- **查询偏好**：在相关性接近的候选里，本 Query 的选择记录优先于全局启动次数；一次选择产生有限倾向，重复选择逐渐稳定顺序。完整名称与明确用户 Alias 继续受保护。
- **性能与召回平衡**：取消与相关性无关的前缀词元截断；混输查询允许汉字、拼音、英文共同解释；在可证明不漏召回处用稀有锚点/必要条件交集收窄候选，并复用工作线程匹配缓冲。

## User Stories

1. 作为 Kite 用户，我希望只输入一个字母时也能找到名称内部含该字母的应用，以便不必记住完整前缀。
2. 作为 Kite 用户，我希望只输入一个拼音首字母时也能命中任意音节位置的对应应用，以便「向日葵」类名称可用首字召回。
3. 作为 Kite 用户，我希望单字符输入不要启用拼写纠错，以免无关近似结果挤占列表。
4. 作为 Kite 用户，我希望两三个字符的连续片段能稳定召回包含该片段的应用，以便短缩写仍可用。
5. 作为 Kite 用户，我希望两三个字符的缩写只在有词首/首字母等依据时才成立，以免偶然词中碎片变成高分命中。
6. 作为 Kite 用户，我希望两三个字符的非连续匹配必须保持顺序且间隔合理，以免乱序字符拼出假命中。
7. 作为 Kite 用户，我希望较长输入继续支持多词、混拼音、跳字和纠错，以便复杂 Query 不因本轮改动变差。
8. 作为 Kite 用户，我希望同一 Query 下完整名称精确匹配始终优先于词中偶然片段，以便排序仍可预测。
9. 作为 Kite 用户，我希望用户 Alias 和明确内置别名继续受保护，以便个性化习惯不被历史或片段匹配抹掉。
10. 作为 Kite 用户，我希望连续且紧凑的匹配高于间隔很开的同字符命中，以便「visual code」比零散字母拼凑更靠前。
11. 作为 Kite 用户，我希望词边界命中的片段高于词中间的同等片段，以便「ter → Terminal」优于无关词中「ter」。
12. 作为 Kite 用户，我希望拼音命中尽量映射回原名称位置再比较，以便不把长拼音串的位置和中文名位置混比。
13. 作为 Kite 用户，我希望多路通道命中同一段内容时不要叠加成异常高分，以便分数可解释。
14. 作为 Kite 用户，我希望同一 Query 下我上次选过的应用在相关性接近时优先出现，以便纠正一次排序就能持续生效。
15. 作为 Kite 用户，我希望重复选择同一目标后顺序更稳定，以便形成肌肉记忆。
16. 作为 Kite 用户，我希望一次偶然选择只产生有限倾向，以免误点永久锁死首位。
17. 作为 Kite 用户，我希望输入另一个软件的完整名称时，昨天常用软件不能抢第一，以便明确意图优先。
18. 作为 Kite 用户，我希望关闭或清空历史后偏好反馈立刻消失，以便个性化受我控制。
19. 作为 Kite 用户，我希望全局启动次数不能压过本 Query 的明确选择记录，以便「这个 Query 就开这个」更可靠。
20. 作为 Kite 用户，我希望质量层级不被纯数值重排抹掉，以便明确匹配保护真正贯穿最终列表。
21. 作为 Kite 用户，我希望检索在个性化加分前不提前截断，以便偏好有机会作用于更宽的候选集。
22. 作为 Kite 用户，我希望拼音/英文混输 Query 能共同参与解释，以便「微信xin」「w微」类输入不因 ASCII 开关丢失召回。
23. 作为 Kite 用户，我希望前缀召回不因固定枚举上限漏掉正确词元，以便同前缀应用仍可进入验证。
24. 作为 Kite 用户，我希望常见短 Query 的输入延迟不因扩大候选而明显变差，以便搜索仍保持即时感。
25. 作为 Kite 用户，我希望空 Query 的固定项和最近使用行为保持不变，以便默认列表习惯不受影响。
26. 作为 Kite 用户，我希望 Pin 在非空 Query 继续生效且不与历史叠加越过保护界限，以便固定项仍可控。
27. 作为 Kite 用户，我希望网页搜索、系统入口和 Everything 文件结果的边界不因本轮应用排序改动被破坏，以便混合结果仍可用。
28. 作为 Kite 用户，我希望规则对所有应用一致，不写产品专属分支，以便新安装软件获得同样体验。
29. 作为维护者，我希望固定 Query 样本能分别记录短输入覆盖、Top1/MRR 和偏好生效情况，以便每轮优化有证据。
30. 作为维护者，我希望匹配证据能解释「为何这个候选靠前」，以便排查排序回归不必猜常量。
31. 作为维护者，我希望索引漏召回、验证拒识和排序错误能分别定位，以便知道该修哪一层。
32. 作为维护者，我希望候选收窄有可证明的必要条件，以便优化查询成本时不静默丢正确候选。
33. 作为 Kite 用户，我希望历史身份迁移后偏好仍指向同一可启动对象，以便升级不丢习惯。
34. 作为 Kite 用户，我希望中英文、拼音、别名、缩写与模糊 Query 的相对优先级保持清晰，以便不必猜测匹配方式。
35. 作为 Kite 用户，我希望相关性接近时短名应用可适度靠前，但不能压过明显更精确的匹配，以便同分列表更友好。
36. 作为维护者，我希望统一入口成为主测试缝，以便 UI 不再各自实现排序分叉。
37. 作为 Kite 用户，我希望托盘重扫后当前 Query 结果仍走同一排序管线，以便行为一致。
38. 作为 Kite 用户，我希望滚动加载更多结果时顺序与首页一致，以便不会翻页后顺序跳变。

## Implementation Decisions

- 保持扫描、检索、历史存储、UI 各自职责。本轮只改搜索内核与主结果管线，不重写扫描、图标和启动逻辑，不引入插件系统。
- 主流程收敛为单一最终排序：多路召回 → 候选验证（保留稳定 id 与匹配证据）→ 读取内存中的 Query 偏好/历史/固定信息 → 统一计算质量与偏好 → 一次排序并截取 Top N → 物化展示对象。UI 只消费该入口，不再「先截断再加分」，也不在层排序后再做纯分数重排。
- 质量层级成为显式排序字段（或等价的第一排序键），禁止用「加分后的数值落在哪个区间」重新猜测层级。
- 候选匹配证据至少包含：命中字段（真实名称/显示名/明确别名/拼音/系统搜索关键词）、匹配方式（精确/词首/连续片段/缩写/跳字/纠错）、匹配位置与覆盖（起点、连续段、间隔、覆盖比例）、纠错代价（实际编辑距离）。展示对象可继续使用简化的 `matched_by`，但排序必须使用完整证据。
- 排序原则：明确名称与用户 Alias 受保护；同等可信度下完整词、词边界、连续且紧凑匹配更靠前；偶然词中片段与高代价纠错靠后。不照抄外部产品的固定分档常量；拼音位置映射回原名称后再比较。
- 多通道命中同一段内容时去重贡献：证据可保留多路以供解释，分数不得对同一覆盖区域重复叠加。
- 短输入策略分档：1 字符允许名称内部、英文词首、拼音首字母任意位置，禁用纠错；2–3 字符支持连续片段与有依据缩写，非连续须顺序/间隔/重复次数验证；更长输入保留现有多词、混拼音、跳字和纠错。
- 拼音候选生成不再由「纯 ASCII Query」总开关一刀切；允许汉字、拼音、英文共同参与解释。候选生成与验证同步调整，不能只删一个判断。
- 前缀枚举取消与相关性无关的固定小上限，或改为完整分批扩展；不能依赖其他通道碰巧补回正确词元。
- 拼音倒排在能证明不漏召回处改为稀有锚点或必要条件交集；无法安全缩小的混输查询保留宽候选。Matcher/匹配缓冲优先在工作线程复用，避免每 Query 重建。
- 查询偏好规则：在相关性接近（同层或相邻层且证据质量接近）的候选间，本 Query 选择记录优先于全局 Usage；一次选择有限加分，重复选择对数式稳定；完整名称精确匹配与用户 Alias 不被偏好越过。不把「前缀/词首/缩写/简拼」锁成完全不可跨越的小层级，允许相近质量竞争。
- Pin 与历史取较大者、不叠加越过保护界限的既有约束保留。空 Query 列表逻辑不在本轮重做。
- 优先保证正确候选稳定出现在用户需要的位置，而不是继续堆叠新通道。无法安全缩小的查询宁可保留宽候选，再由证据排序收敛。
- 不引入云服务、行为上传、向量检索或新的外部搜索引擎。索引与历史继续使用现有本地结构。

## Testing Decisions

- 好测试只断言外部可见行为：给定固定索引 fixture、Query 和个性化状态，观察最终有序列表中的目标身份、相对顺序、禁止项，以及关闭历史后的行为变化。不断言内部函数调用次数或具体分数常量。
- 唯一主测试缝为统一搜索入口：输入 Query + 同代检索索引 + 个性化状态（Usage / Query 配对 / Pin），输出有序 TopK。短输入覆盖、证据细排、偏好反馈、截断顺序修复全部走这一缝。
- 沿用并扩展 `tests/search_cases.json` 与 eval 基线：增加 1 字符、2–3 字符片段/缩写/乱序、混输拼音、「偏好生效但完整名仍保护」、以及「历史不能把弱匹配抬进明确匹配之前」样本。期望指向稳定 fixture id，不只是显示名。
- 对偏好反馈使用隔离历史状态：同一 Query 多次选择某目标后，在相关性接近的候选中前移；清空或暂停记录后立刻失效；输入另一软件完整名时不得被历史抢首位。
- 对短输入与召回完整性：构造同前缀多词元、名称内部单字符、拼音首字母中间位置、ASCII+汉字混输样本，验证目标进入 TopK，而不是只验证首位截图。
- 对排序证据：用成对样本比较「连续 vs 跳开」「词边界 vs 词中」「精确 vs 高代价纠错」「Alias/精确 vs 历史偏好」，断言相对顺序。
- 对性能：在固定中大型索引上记录常见短 Query 与长 Query 的检索耗时 P50/P95，确保扩大召回没有把热路径打成不可用；收窄候选处须有「不漏召回」的正向样本。
- prior art：`tests/search_cases.json` 驱动的 search eval、`history` 分层与保护不变量单测、search 模块内的 Query→Top 应用回归。Windows 实机可复测若干短 Query 与偏好纠正，但算法正确性以可复现 fixture 测试为准。
- 检查通过标准：`cargo test` 全绿；新增样本相对基线 Top1/MRR 不恶化，短输入覆盖与偏好生效样本通过；无产品名专属分支。

## Out of Scope

- 插件系统、云同步、遥测、AI/向量/Embedding/LLM 搜索、Tantivy、SQLite FTS、Elasticsearch。
- 重写扫描、入口去重、图标缓存、启动逻辑或 Everything 文件搜索。
- 照搬 ZTools/Fuse.js 的分值常量或完整算法；只借鉴覆盖、证据排序与偏好反馈原则。
- 为任何品牌、产品名、exe 写扫描或打分特例。
- 重做 UI 视觉、空 Query 默认列表产品定义、文件搜索默认开关。
- 新的持久化数据库或跨平台搜索栈。
- 签名、版本号、推送、合并和发布。

## Further Notes

- 前一轮 `search-experience-next` 已解决索引后台刷新、图标链路、基础召回特征与 History 分层的首版落地；本轮聚焦「让已有能力贯穿最终结果」：统一最终排序、补齐短输入/混输覆盖、引入匹配证据、收紧查询偏好与查询开销。
- 建议执行顺序：先修最终排序与截断 → 补齐短输入和混输召回 → 引入匹配证据细排 → 调整查询偏好反馈和查询开销。这样每一步都可用同一测试缝验收，避免历史加分系数单独漂调。
- 领域词汇沿用 `CONTEXT.md`：AppItem、Query、MatchScore、Alias、Usage、Recency、Query History、FinalScore、明确匹配保护、Pin。规格中的「匹配证据」「质量层级」「查询偏好」若进入长期设计，再补充领域文档。
- 「相关性接近」在实现上应定义为可测试的相邻质量层或证据分档，而不是开放阈值拍脑袋；具体分档边界由实现结合样本确定，并写入测试期望。
- 本规格不打开新的工作树；后续实现若需并行，再按项目约定隔离。
