Status: ready-for-agent
Type: enhancement

## Problem Statement

Kite 已能从开始菜单、桌面、Scoop、App Paths 和 UWP 建立 AppItem 索引，并结合 MatchScore、Usage、Recency、Query History 与 Pin 排序。但索引主要在启动或手动重扫时重建：运行中安装、卸载或修改入口后，Query 可能继续显示旧结果。不同来源指向同一程序时，原始 exe 名、友好快捷方式和历史记录也可能分散或竞争；图标在来源变化后可能仍显示旧缓存或占位符。用户需要的是及时、安静、稳定的搜索结果，而不是理解各入口来自哪里。

本轮以 Win32 应用入口的自动更新、通用降噪、个性化排序和图标可用性为一个搜索体验闭环。当前已修复的英文词尾误召回、原始 App Paths 入口降序、回收站图标生成及部分损坏缓存，作为回归基线保留；控制面板仍显示不对应的通用系统图标。

## Solution

Kite 在运行中感知已支持的 Win32 入口变化，后台合并或重建受影响的索引，并自动刷新当前 Query。相同启动语义的入口只展示一个首选结果；不同启动语义或无法可靠确认同一应用的入口仍可搜索，原始入口适度靠后。启动过的 AppItem 在相关 Query 中更容易再次找到，同时保留明确匹配保护和用户 Pin 的优先级。图标缓存随来源变化更新，提取失败有可辨认的回退，且图标工作不阻塞输入和搜索。

验收以真实 Windows 上的安装、卸载、快捷方式变更、重复入口、历史排序和图标显示为准；Rust 回归测试锁定可复现的输入与结果。使用固定 Query 样本记录相关性和端到端延迟基线，再决定分数或缓存策略，不以单个产品名称写特例。

## User Stories

1. 作为 Kite 用户，我希望运行中安装应用后无需重启或手动重扫就能搜到它，以便立即启动。
2. 作为 Kite 用户，我希望卸载应用后失效入口及时消失，以便不会打开一个不存在的 target。
3. 作为 Kite 用户，我希望重命名开始菜单或桌面快捷方式后 Query 使用新名称，以便搜索结果与系统入口一致。
4. 作为 Scoop 用户，我希望新增、移除或更新 shim 后结果自动变化，以便包管理器安装的软件可用。
5. 作为通过 App Paths 注册程序的用户，我希望注册入口变化后索引自动更新，以便没有快捷方式的程序也能找到。
6. 作为正在输入的用户，我希望后台更新完成后当前 Query 的结果自动刷新，以便不用清空重输。
7. 作为正在查看列表的用户，我希望更新期间旧索引仍可用，完成后结果一次性切换，以便列表不会短暂清空或来回跳动。
8. 作为 Kite 用户，我希望安装器一次写入多个文件时只触发必要的刷新，以便搜索窗口保持流畅。
9. 作为 Kite 用户，我希望某个目录或快捷方式解析失败时其他应用仍可搜索，以便局部错误不拖垮整次更新。
10. 作为 Kite 用户，我希望托盘“重新扫描应用”继续可用，以便在系统通知丢失时主动恢复结果。
11. 作为 Kite 用户，我希望同一个程序的桌面、开始菜单和注册表入口不要占据多个相邻位置，以便更快识别目标。
12. 作为 Kite 用户，我希望带不同启动参数或独立功能的入口保留，以便降噪不会误删可用命令。
13. 作为 Kite 用户，我希望友好名称优先于同一安装中的原始 exe 文件名，同时仍能找到原始入口，以便日常搜索清楚且高级用法不受影响。
14. 作为 Kite 用户，我希望规则对所有应用一致，而不是只处理某个办公软件，以便新安装的软件也获得同样体验。
15. 作为 Kite 用户，我希望启动过的 AppItem 在相关 Query 中更容易再次出现，以便 Kite 能记住我的选择。
16. 作为 Kite 用户，我希望短 Query 不再被无关系统工具或词尾匹配挤占，以便真正想找的应用容易进入首屏。
17. 作为 Kite 用户，我希望明确匹配的其他应用不会因为一次历史启动而被弱匹配压下去，以便排序仍可预测。
18. 作为 Kite 用户，我希望关闭历史记录或清空历史后排序立即反映这个选择，以便个性化受我控制。
19. 作为 Kite 用户，我希望安装路径、入口来源或快捷方式变化后，已有 Pin、Alias 和 Query History 尽可能继续指向同一可启动对象，以便升级不丢个人习惯。
20. 作为 Kite 用户，我希望程序换了图标后结果显示新图标，以便列表与当前安装状态一致。
21. 作为 Kite 用户，我希望无扩展名但实际包含 ICO 内容的快捷方式图标源也能正确显示，以便 MSI 安装的软件不被画成通用白纸图标。
22. 作为 Kite 用户，我希望优先图标源无效或只给出通用文件图标时，Kite 能尝试快捷方式 target 的应用图标，以便列表仍有辨识度。
23. 作为 Kite 用户，我希望图标源不存在、损坏或完全透明时仍有可辨认的图标回退，以便不会出现大量空白图标。
24. 作为 Kite 用户，我希望图标刷新与文件类型图标复用不拖慢输入，以便搜索始终即时响应。
25. 作为 Kite 用户，我希望开始菜单多层文件夹中的快捷方式也能被索引，以便删除桌面快捷方式后应用仍可搜索。
26. 作为 Kite 用户，我希望控制面板等 Shell 虚拟入口显示当前 Windows 的真实系统图标，以便不会把通用软件图标误认成该入口的图标。
27. 作为已经安装 Kite 的用户，我希望升级修复后旧的错误图标缓存自动更新，以便不必手动删除缓存目录。
28. 作为 Kite 用户，我希望中文、拼音、英文、缩写和模糊 Query 都有稳定排序，以便不必猜测特定匹配方式。
29. 作为维护者，我希望可以复现同一批 Query 的首位结果、重复项、图标覆盖和延迟，以便每轮优化有证据可比较。

## Implementation Decisions

- 保持扫描、搜索召回与排序、历史存储、图标缓存、Iced 界面各自的职责；界面只消费索引快照并触发搜索刷新，不承担入口去重或打分逻辑。
- 监听用户和公共开始菜单、桌面、已配置 Scoop shim 目录，以及当前支持的 App Paths 注册表视图。变化通知合并为后台刷新；监听失败或漏报时保留手动重扫。不得每隔固定时间扫描整个系统。
- 同一时刻最多进行一次索引构建；突发事件合并，构建期间到来的变化在完成后继续处理。发布完整新快照，旧构建结果不得覆盖较新的状态；当前 Query 随快照更新。
- 继续复用现有快捷方式解析缓存。缓存命中取决于入口内容的可验证变化，不能把“缓存有效”当作“索引不需要刷新”。
- Win32 入口同一性的判断以规范化 target、启动参数及会影响启动语义的上下文为基础，来源名称仅决定展示优先级。不能仅凭同名或共同父目录合并，也不能把用户 Query 当作待执行命令。
- 首选开始菜单或桌面的可读入口；App Paths 与原始 exe 可搜索但适度靠后。对于不能确认相同启动语义的近似入口，先保留可启动结果，避免错误去重。
- AppItem 身份在来源变化时尽量稳定。若现有持久化 id 必须变化，应迁移或兼容 Usage、Query History、Pin 和 Alias，且不得把历史转给不同的可执行 target。
- 保留 MatchScore 为主信号、Query History 为重要个性化信号，以及明确匹配保护。Pin 与历史加分不叠加越过保护界限；同一程序的入口展示优先级可单独处理，不能无条件降低所有精确匹配。
- 系统工具、普通应用、网页搜索与 Everything 文件结果维持各自的召回边界；本轮只改善系统工具噪声对应用搜索的影响，不改变文件搜索的可选开关和 Everything 依赖方式。
- 快捷方式图标源允许通过文件内容识别无扩展名的 ICO；优先源无法给出应用图标时，再尝试已验证的启动 target。不能把来源文件的通用白纸关联图标当作提取成功，也不能因此绕过 target 回退。
- Shell 虚拟入口优先从当前系统命名空间对象取得对应图标；仅在语义确实对应时使用 stock icon 回退。通用软件图标不能冒充控制面板等具体系统入口。
- 图标以可验证的源变化失效，损坏或全透明的缓存重新提取；提取策略修正后还须让旧版缓存中内容有效但语义错误的通用图标重新生成，无需用户手工清缓存。系统虚拟入口和文件类型图标保留统一回退。更新后的图标必须在实际列表中可见，不能只修改磁盘 PNG 而被界面缓存继续显示旧图。
- 对图标缓存增长和文件关联图标的失效方式分别记录与验证，不把 AppItem 索引刷新、快捷方式解析缓存和 PNG 图标缓存混成一个固定 TTL。
- 开始菜单扫描覆盖常见的多层程序文件夹，同时保留不跟随 junction、目录/总量上限和后台预算，避免为增加覆盖率而造成启动卡顿。
- 不引入云服务、用户行为上传或新的搜索索引数据库。历史继续使用现有本地 SQLite 决策，文件搜索继续遵守 Everything 的既有 ADR。

## Testing Decisions

- 主要测试缝为“受控入口变化 → AppItem 索引快照 → 同一 Query 的最终结果”。测试观察可见名称、顺序、target、图标和可启动性，不断言内部函数调用次数或具体分数常量。
- 对扫描器使用临时目录和可控注册表测试替身或隔离环境，覆盖创建、删除、改名、多层开始菜单、参数不同、来源重复、坏快捷方式和突发事件；将 NVIDIA App 这种位于“Programs / 厂商 / 应用快捷方式”层级的 Win32 入口纳入端到端样本。一条坏入口不能清空整份索引。
- 对搜索管线使用固定的中英文 Query 样本、别名、拼音、系统工具、原始 exe 与友好入口，验证首位或前三位、重复数量、无关结果和明确匹配保护。已有 WPS/Aurora、`ter`/XTerminal 与回收站回归用例作为先例，不在生产规则中写入这些名称。
- 对历史使用隔离的本地库，验证一次成功启动后的 Query History、Frequency 和 Recency 变化，以及清空或暂停记录后排序的外部行为；验证身份迁移不误绑 Pin 和 Alias。
- 对图标使用真实 Windows 图标提取、损坏缓存、源更新与显示刷新测试；加入“无扩展名但头部为 ICO 的 MSI 图标源”“优先源只返回通用白纸图标而 target 带应用图标”“升级前缓存了错误但有效的 PNG”三个回归用例。对控制面板、回收站等 Shell 虚拟入口，在同一 Windows 上核对列表图标是否对应系统对象，而不只检查 PNG 是否存在。在真实列表中检查系统入口、普通 exe、快捷方式、Scoop、UWP 和常见文件类型的图标覆盖率。
- Windows 端到端验收覆盖开始菜单、桌面、Scoop、App Paths 的安装/卸载/改名。以最后一次入口变化后 5 秒内看到稳定结果为目标，记录超时和原因；更新过程中搜索可用，且一次安装事件不会产生持续重扫。
- 用同一套匿名化 Query 与索引样本记录 Top 1/Top 3 命中率、重复入口数、图标覆盖率和“输入 → 列表更新”的 P50/P95/P99。与改动前 Kite 基线比较；若与 Flow Launcher 比较，应在同机、同查询和相近索引覆盖下实测，不能用唤起速度代替搜索相关性。
- 沿用当前 Rust 回归测试与 Release 构建检查；Windows 行为须在真实机器上做可见结果和进程稳定性验证，编译通过不算完成。

## Out of Scope

- 自建 NTFS 全盘文件索引、替换 Everything、改变文件搜索默认开关。
- UWP/Store 安装事件的实时监听；本轮仍通过启动扫描与手动重扫覆盖 UWP，另行评估可靠的系统事件源。
- 为任何特定品牌、产品名、exe 名或目录写专属搜索规则。
- 插件系统、云同步、遥测、AI 搜索、跨平台实现，以及界面视觉重做。
- 固定间隔全盘重扫、仅凭一个时间 TTL 判断所有缓存过期。
- 签名、版本号、推送、合并和发布。

## Further Notes

- 当前索引在启动及托盘手动重扫时构建；快捷方式解析缓存按路径、修改时间和大小复用，图标缓存另有来源时间检查。三者生命周期不同，需要分别验收。
- Flow Launcher 和 PowerToys Run 的程序源实现提供了入口变化监听、突发事件合并与来源去重的参考；这里只借鉴可验证的行为，不照搬其技术栈或所有缓存时长。
- 本机 CC Switch 的桌面快捷方式指向现存的应用 exe，图标位置是 MSI 安装目录下无扩展名的 `ProductIcon`；文件头为有效 ICO（`00 00 01 00`）。当前缓存生成的是通用白纸 PNG。该应用的开始菜单快捷方式又比现有扫描深度多一层，因此这里只把它作为一般性“无扩展名 ICO + 深层快捷方式”验收样本，不添加产品名特例。
- 本机 NVIDIA App 是 Win32 快捷方式，Windows 开始菜单能找到，target exe 也存在；其快捷方式在“Programs / NVIDIA Corporation / NVIDIA App”层级。现有扫描从开始菜单根目录最多遍历两层，实际文件位于第三层，故未进入快捷方式缓存和 AppItem 索引；此例不是 UWP 收集失败，也不应给 NVIDIA App 单独补入口。
- 本机控制面板缓存不是空文件，而是当前代码所选的通用软件 stock icon；截图中的小图标与缓存一致。此例验证“图标内容正确”，不应误写为“图标提取失败”。
- 先建立可复现的 Query/索引评估样本和当前基线，再调整去重与个性化权重；自动刷新可以独立验收，但最终仍以完整搜索列表的表现为准。
- 后续由 `/to-tickets` 把索引刷新、身份与降噪、历史排序、图标和实机验收拆成有依赖关系的任务；本规格本身不代表功能已实现。
