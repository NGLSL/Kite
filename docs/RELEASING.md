# Kite 发布流程

## 分工

本机负责实现、版本号、维护者说明、必要静态检查和 Git 操作。GitHub Actions 负责完整检查、正式 Release 编译、官方插件与 NSIS 打包、安装验收、校验和、构建产物和 GitHub Release 上传。本机不重复这些正式构建和安装操作。

本文件是当前项目发布流程的依据；历史发布笔记或通用 release skill 中的本机构建要求以此处为准。发布或推送需要用户明确授权，修改本流程不会自动发布版本。

## 本机准备

1. 查看分支、工作区及目标 diff，保留无关未提交改动；按本次授权决定分支顺序和提交范围。
2. 发布版本时更新 `Cargo.toml`、`Cargo.lock`，维护 `docs/releases/vX.Y.Z.md`。版本说明写清用户可见变化、升级影响和已知限制。
3. 默认执行 `cargo check --locked --offline` 与 `git diff --check`。按改动补充目标文件的格式或脚本语法检查；只为定位具体故障运行相关既有测试。依赖未缓存时先获取依赖。
4. 不把全量 `cargo test`、`cargo build --release`、官方插件打包、NSIS 或安装覆盖作为本机发布前置条件。需要实际界面诊断时使用开发运行，并明确记录验证范围。

## Actions 工作流

| 入口 | 职责 | 完成产物 |
| --- | --- | --- |
| `ci.yml` | PR 和 `main` 提交的完整既有检查、编译及静态安装契约 | 精确提交的 CI 状态 |
| `package-windows.yml` | 复用的正式构建、NSIS、独立 Windows runner 安装验收 | 已验收的安装器、校验和、负载清单、安装报告 |
| `build.yml` | 手动请求候选安装包，调用相同的打包与安装验收路径 | Actions artifact，不创建公开 Release |
| `release.yml` | 校验正式 tag 与 CI，调用打包验收，再发布 | GitHub Release 安装器、校验和和安装报告 |

`scripts/build-installer.ps1` 是 Actions 的唯一安装包构建入口，一次完成官方插件、主程序与 NSIS；工作流不在其前重复构建同一套 Release 产物。正式构建使用已有 lockfile；安装包和正式报告脚本仅接受 GitHub Actions 环境，避免把本机临时产物当作正式发布证据。

## 正式发布顺序

1. 提交维护者说明和版本修改，按已授权的分支策略把目标提交合入 `main`。
2. 等待该精确 SHA 的 `ci.yml` **push main** 运行成功；PR 检查或其他提交的绿灯不能替代。
3. 在这个提交上创建、推送注释 `vX.Y.Z` tag。tag 版本须与 `Cargo.toml` 一致，tag 提交须包含于 `origin/main`。
4. Release 先校验上述条件，再构建安装器；安装验收在独立的干净 Windows runner 执行。
5. 安装验收成功后才生成正式报告并上传。报告中的提交、版本、安装器大小和 SHA-256 必须与下载到发布 job 的同一份产物一致。
6. 检查工作流成功、公开 Release 状态和资产信息后报告完成。任何失败先修复并重跑对应 Actions，不在本机补一个包替代失败的 CI 证据。

手动重跑 Release 时选择已有发布 tag，仍执行相同门禁。需要先取安装包供人工验证时运行 **Build Windows application**，从该次成功运行下载已验收 artifact。

## 安装验收与证据

独立 Windows runner 对同一份安装器执行静默安装、同版本覆盖安装和卸载，核对主程序、官方插件与运行资源哈希、安装和卸载注册表信息，并检查用户数据标记在覆盖及卸载后保留。验证使用 runner 的隔离目录；不连接开发者本机。

文件索引读取组件另行验证注册、同版本覆盖时实际替换宿主、以及随卸载移除。服务应保持按需启动，空闲时停止；覆盖前后核对 NTFS 文件身份变化和最终哈希，避免相同版本的相同哈希掩盖没有更新组件的情况。

文件同步专项验收通过安装后的诊断入口复用生产控制器，在 runner 隔离目录创建超过 65,536 个真实存活文件，核对查询、同基库重启续读和 32 MiB 日志切段后的回收。随后仅在一次性 GitHub hosted runner 的非系统 NTFS 暂存卷，对同批文件实际改名，推进日志保留范围越过已停止的游标；普通启动必须自动进入恢复并生成可查询的新代际。整个过程保持 journal 身份、容量和分配配置不变，不发送手动重建命令。本机 journal 不作修改。此流程使用真实 NTFS 与 USN，不写入模拟索引；专项结果随安装验收报告绑定同一份安装器，失败阻止发布。

`installer-validation.json` 绑定具体提交、版本和安装器 SHA-256，记录真实执行结果；`payload-manifest.json` 记录构建负载。静态的 `scripts/test-installer-upgrade.ps1` 是源码契约检查，不能替代实际安装验收。正式发布附带 `kite-setup.exe`、`kite-setup.exe.sha256` 和 `installer-validation.json`；主程序及负载清单仅作为 Actions 内部产物。

后台重试验收继续复用上述隔离 profile，使用真实 Windows 独占文件锁暂时阻止读取已有索引清单，观察第一次 30 秒、第二次 60 秒等待。释放锁后不发送人工重试或重建命令，必须自动恢复为就绪、复用同一索引代际并清零重试计数，查询仍正确。此过程不修改清单内容，实际等待及恢复结果随安装器报告记录。

验收报告必须区分同版本覆盖、旧版本迁移、文件索引功能和人工桌面交互。干净 runner 的静默安装不会验证 UAC 拒绝、多屏、快捷键手感或长期在线稳定性；这些按具体变更记录为单独的人工或专项验收。

## 完成标准

- 精确提交的 main CI 成功，注释 tag、版本号和提交关系通过门禁。
- 打包及独立 runner 安装验收成功，正式报告读取该次验收证据。
- GitHub Release 已发布，安装器、校验和与验收报告齐全且相互匹配。
- 最终说明分别列出源码检查、Actions 构建和安装验收、实际上传状态及人工未验证部分。
