# 发布说明维护

每个正式版本在创建 tag 前维护一份同名文件，例如：

```text
docs/releases/v0.3.0.md
```

文件由维护者填写用户真正关心的内容，建议包含以下部分：

```markdown
# Kite v0.3.0

## 版本重点

用几句话说明这一版解决了什么问题，以及用户能直接感受到什么变化。

## 新功能

- 用户可见的新能力和使用方式

## 修复

- 触发条件、根因和修复后的行为

## 升级影响

- 配置、快捷键、安装目录、资源文件或兼容性是否有变化

## 已知限制

- 仍然存在的限制，以及临时规避方式
```

发布工作流会自动把这份说明与机器生成的信息合并到 GitHub Release：tag 提交、上一个版本、提交范围、`cargo test`、release 构建、NSIS 构建、安装包大小和 SHA-256。没有对应说明文件时，工作流仍会生成构建报告，但会明确提示缺少维护者说明。

推荐流程：

1. 更新 `Cargo.toml` 版本号。
2. 新建 `docs/releases/vX.Y.Z.md`，写清用户可见变化和升级影响。
3. 合并到 `main`，确认 CI 通过。
4. 创建并推送 `vX.Y.Z` tag。
5. 等待 Release workflow 构建并发布安装包，检查报告和 SHA-256。
